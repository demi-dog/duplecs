# Changelog

All notable changes to duplecs are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and version numbers follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Every entry states whether the wire format changed: both sides of the wire must run the same duplecs build, so a wire change means upgrading the server and its clients together — check here before upgrading.

## [Unreleased]

### Added

- `InheritsPrivacyThrough`, a server-side relation that lets an entity inherit visibility through a relationship it already has: `world:add(item, pair(InheritsPrivacyThrough, jecs.ChildOf))` makes the item's entity-level visibility follow whatever its parent allows, exactly as a `pair(InheritsPrivacy, parent)` would, kept in sync with the `ChildOf` pair automatically — parenting adds the inherited gate, unparenting removes it, and reparenting moves it, so for containment hierarchies (a room's contents, a chest's items, a player's inventory) picking something up and reparenting it are one act, with no second pair to keep in step and no forgotten one to leak or lose state. It composes with direct `InheritsPrivacy` pairs and with other relations inherited through (every gate intersects, and a group reached several ways stays inherited until the last way goes), follows every `InheritsPrivacy` rule (chains, several parents, `ExportsPrivacy`, no cycles — a pair closing one is removed and errors, the inheriting pair or the relation pair, whichever closed it), and takes existing pairs of the relation into account the moment it is added. The relation must carry `pair(jecs.OnDeleteTarget, jecs.Delete)` as `jecs.ChildOf` does, so a parent's deletion deletes the entity rather than widening it; one without it is refused with an error naming the leak, as are an unpaired add and a `jecs.Wildcard` relation. An exclusive retarget ships exactly the old-parent -> new-parent difference — nothing reaches a client admitted by neither parent. The component rides the shared set (inert on client worlds), and the [visibility inheritance guide](docs/guides/006-visibility-inheritance.md) now recommends it over hand-kept `InheritsPrivacy` pairs wherever the group is also the entity's container. Purely additive — the wire format is unchanged.
- `ExportsPrivacy`, a server-side entity-level filter component that narrows what an entity's `InheritsPrivacy` inheritors receive *below* the entity's own visibility, leaving the entity itself untouched — a chest visible to everyone whose item entities reach only the player who opened it, or an enemy base shown to all as a map marker whose contents replicate only to players nearby. The value follows `Private`'s rules exactly (an empty table hides every inheritor, a populated one is a whitelist or blacklist, `nil` warns and is rewritten to an empty filter, malformed values revert and error, departed clients are pruned), absence changes nothing, pairing it errors, and `edit_exported_privacy` edits membership like `edit_entity_privacy`. It can only ever narrow — an inheritor stays visible to at most the clients its group is — and exports chain down inheritance the way inherited filters do. Editing an export restages only the inheritors whose visibility changed, never the entity's own cells. The component rides the shared set (inert on client worlds) and is documented in the [visibility inheritance guide](docs/guides/006-visibility-inheritance.md), which also now covers the gate-entity pattern for the opposite shape (contents visible where their container is not). The two prune warnings for filters naming untracked clients now begin `the Private filter named` / `the Private blacklist named` (previously `a Private ...`), so they can name either component. Purely additive — the wire format is unchanged.
- `duplecs.shared` now accepts `nil` to **pre-register** the component set before any world exists, for schema modules written in jecs's top-level pre-registration style (`jecs.component` / `jecs.tag` / `jecs.meta` before `jecs.world`): `local net = duplecs.shared(nil)` mints the set once, definitions can tag `net.Networked` and register `net.Serdes` hooks through `jecs.meta` at definition time, and every world created afterwards holds the same set — `duplecs.shared(world)` and both halves recognize it instead of minting per world. Like all jecs pre-registration it must run before world creation: a world created too early errors at its first duplecs contact rather than corrupting silently. `Serdes` registrations made through `jecs.meta` validate at each world's first duplecs contact instead of at their own call site. See [pre-registration in the getting-started guide](docs/guides/001-getting-started.md#alternative-pre-registering-before-any-world). Purely additive — the function-of-world style is unchanged, and the wire format is unchanged.

- Tracking modes can now be designated **per pair target** at the schema level: adding a tracking tag paired with a target to a definition — `world:add(Transform, pair(Networked, Static))` — makes pairs aimed at that target replicate under the designated mode. `pair(Networked, Static)` beside `pair(NetworkedUnreliable, Dynamic)` on one relation swaps entities between reliable and streamed replication by retargeting a single pair (`jecs.Exclusive` makes the swap one set). Without an unpaired tag, only designated targets' pairs replicate; with one, the designation overrides it per target while everything else follows the plain tag. Designation edits ship nothing while a pair stays replicated, except that leaving `NetworkedUnreliable` restages current values to re-establish the reliable baseline; a designated target that is neither `Replicated` nor named warns at the first pair aimed at it, since a schema-level marker failing silently is almost always a missing name. See the [pairs guide's target-specific modes](docs/guides/003-pairs.md#target-specific-modes). Pairing a tracking tag previously errored (the `<tag> is not meant to be paired!` error is gone, replaced by the designation guards). The wire format is unchanged.

- **Breaking:** Pairs of a **tag** relation now derive serdes hooks from the target definition's own registration automatically: such a pair's data is typed by its target (jecs's rule for `pair(tag, component)`), and a tag relation cannot carry a registration of its own, so registering the target once now covers both its standalone values and every tag-relation pair carrying it as data. A concrete `pair(Serdes, target)` registration on the relation still takes precedence — see the [serdes guide](docs/guides/008-serdes.md). **The wire format version is bumped** (no byte layout changed, but affected schemas' pair values move from the side array into the packet buffer, so mixed builds must be refused rather than misparse): upgrade the server and its clients together.
- `NetworkedUnreliable` can now be added to **tag** definitions, so a tag relation's pairs can stream every frame: pairs with data-component targets carry target-typed values whose serdes hooks derive from the target's registration (the entry above), and those values now ride `generate_unreliable_chunks` like any other unreliable value — e.g. per-target amounts like `pair(Stockpiles, Gold)`. A tag's valueless cells — the bare tag, and pairs targeting tags or plain entities — carry nothing to stream, so they stay on the reliable path exactly as they would under `Networked`. Previously the tag was refused outright (the `NetworkedUnreliable cannot be added to tags!` error is gone), a guard predating serdes target-derivation. The wire format is unchanged.
- A [bandwidth guide](docs/guides/013-bandwidth.md), the byte-side sibling of the performance guide: the exact per-entry cost of everything duplecs puts on the wire, measured packet sizes for representative frames, and budgeting for the join snapshot and the unreliable channel. Its numbers come from a new benchmark, `tests/benchmarks/bench_bandwidth.luau`, and are byte-exact and machine-independent. Documentation only — the wire format is unchanged.
- Every duplecs component now carries a `jecs.Name` in jecs's own dotted style — `duplecs.Networked`, `duplecs.Private`, and so on — so debuggers and state viewers that label components by name (e.g. jabby) render them legibly instead of as bare ids. The names follow the ordinary `jecs.Name` contract (identical on both sides, so a networked pair aimed at a duplecs component maps like any named target), and the `duplecs.` prefix keeps them clear of the plain names schema modules share. The wire format is unchanged.

### Changed

- Clients apply a packet's entity deletions together rather than one at a time, so deleting a group (or revoking a client's view of one) no longer detaches each of its replicated members from the group moments before deleting that member too, and entities that nothing references are deleted without inspecting their dependents at all — reconciling a large group's teardown does less work. The resulting world is the same as before, whatever order the packet lists the deletions in: imported dependents the packet doesn't delete are still detached and survive, and local dependents are still deleted. Two things a `world:removed` hook can observe differ: a replicated member deleted in the same packet as its group sees its pair to the group removed as part of its own deletion (`delete` set, as the server's own cascade removed it) rather than — depending on the packet's order — as a separate detach first, and `get_server_entity` returns `nil` for every entity the packet deletes from inside any hook those deletions fire (previously, entities later in the list still resolved). The wire format is unchanged.

### Fixed

- Renaming an announced definition or named pair target to an empty or over-long name now withdraws its announcement, so clients end the mapping the old name established (a later valid rename announces it again). Previously the refused rename warned but left the stale announcement standing, keeping every client bound to the old name. The wire format is unchanged.
- Adding or removing `Replicated` no longer risks a hidden cost proportional to the world's replicated-entity count: an internal table keyed by full entity ids made Luau rebuild it on nearly every spawn whenever the number of replicated entities sat at (or one below) a power of two while entities churned. Spawn-and-despawn overhead at the benchmark's canonical shape (32 clients, two networked components) drops from ~14x to ~6x the cost of the same lifecycle on a world that isn't networked at all — see the updated tables in the [performance guide](docs/guides/012-performance.md). The wire format is unchanged.
- The same table-rebuild pathology is fixed on the client: the server↔client entity mapping was keyed by full client entity ids, which are brand new for every reconciled creation, so a client whose mapped-entity count sat at (or one below) a power of two during entity churn paid a rebuild proportional to that count on nearly every creation it reconciled — at 1024 mapped entities, a benchmark frame reconciling one creation measured ~47 µs instead of ~5 µs. Stale entity references passed to `get_server_entity` still resolve to `nil`, now via a liveness check rather than key identity. The wire format is unchanged.

## [1.0.0] - 2026-08-12

The initial public release, published to the pesde registry as `demidog/duplecs` and the Wally registry as `demi-dog/duplecs`. Earlier development versions were never published — no public tags, no registry entries — so this changelog starts here, and later releases document their changes against this one.

duplecs is generalized per-world replication for [jecs](https://github.com/Ukendio/jecs): it listens for changes in the server's jecs world, decides what should replicate to whom, packs the result into one filtered packet per client, and reconciles that data back into each client's world. duplecs does not own transport — sending packets to clients is the caller's responsibility, typically using a `RemoteEvent`.

What this release ships:

- **Opt-in replication** — a component reaches a client only when its definition is marked `Networked`, the entity carrying it is marked `Replicated`, and neither is blocked by a `Private` filter.
- **Visibility filters and inheritance** — `Private` filters assigned per entity or per component (an empty one for server-only state, a client-keyed one for whitelists and blacklists), with multiple entities able to inherit one entity's filter so their visibility is edited from a single place.
- **Relationship support** — networked relations like `jecs.ChildOf`, by tagging the relation itself; a pair is never sent to a client who cannot see its target, and per-component filters also prune pairs using that component as a relation.
- **Nothing sent twice** — a change ships the frame it happens and is never re-sent on the reliable path; a client joining later gets one packet holding everything currently visible to them; `NetworkedOnce` definitions ship values only when the component is added.
- **Mapped entity ids** — the server and each client often hold different ids for the same entity, so duplecs maps them both ways on the client: replicated entities map themselves, shared components map by name so definition order can differ between sides, and methods exist for reading or assigning the mappings yourself.
- **Serdes hooks** — give a component's values a byte encoding and they pack into the packet's buffer, for a fraction of the bandwidth; components without hooks ride a plain side array, so day one needs no byte encodings.
- **An unreliable channel** — every-frame changes (e.g. positions, velocities) can be routed through self-contained chunks sized for unreliable transports.
- **Client-side control** — reconciliation overrides put your code between the wire and the world: id translation, prediction gating, and interpolation buffers.

The wire format starts fresh at this release.
